# R1: hybrid retrieval for MCP `recall` (protocol)

Written and committed on 2026-11-18, before the benchmark code or data exist. Nothing below is changed
after a result is seen; a bug fix in the harness that does not change an arm, a parameter or the data is
logged in the report.

## Question

When a person's memory is larger than one `recall` can show, does adding a lexical ranking to the meaning
ranker (fused by Reciprocal Rank Fusion) put the memory that answers a question among the memories shown
more often than production does today, at the same number of memories shown?

## Why now

On 2026-11-18 a defect in the fallback path of `AgentMemory._related` was fixed (PR #175). A proposal then
suggested SQLite FTS5 + BM25 fused with the meaning ranker. Production (infinitomemory.com) runs with
`INFINITO_EMBEDDINGS`, so its `recall` ranks by meaning only (`MeaningRanker`, potion-multilingual-128M
int8) and ignores exact words such as ticket codes or PR numbers. The MCP `recall` path has no benchmark of
its own (noted 2026-11-06). This experiment is that benchmark, and the first decision it informs.

## Arms (all choose among the same active memories, `AgentMemory._active()`)

| Arm | What it is |
|---|---|
| **A, baseline** | Production: `MeaningRanker.rank` over every active memory, top k. This is the store-everything semantic RAG baseline at equal budget: every memory is kept and the k closest by meaning are shown. |
| B | The fallback after PR #175: `store.search` (hashed lexical + vector score), top k. |
| C | FTS5 only: an in-memory FTS5 table (`unicode61 remove_diacritics 2`), the question's word tokens joined with OR, ordered by `bm25`, top k. |
| D | RRF of A's top 40 and C's top 40, k_rrf = 60, top k. |
| E | RRF of A's top 40 and B's top 40, k_rrf = 60, top k (a hybrid without FTS5). |

Ties: RRF ties break by A's rank, then by age. No arm has a parameter tuned on this data; the numbers above
are fixed now (40 and 60 come from the proposal and the RRF paper's default).

Budget: every arm shows the same k memories (k = 20, today's `RECALL_TOP_K`; k = 5 reported as well), so
the context handed to the assistant is the same size for all arms.

## Data

Synthetic, in Spanish, generated by a fixed-seed program; no memory of any real person is used and no
model is called. Each split builds its own memory through `AgentMemory.remember` (the real write path,
with its filters and dates) and fills it with generated distractors up to N memories.

Families of questions, per split:

| Family | Count | Gold memory | Question |
|---|---:|---|---|
| F1 exact identifiers | 40 | "El ticket ATL-4821 del proyecto Atlas: ..." or "El PR #482 de Brisa ..." | names the code or number |
| F2 client and topic | 36 | "Con Acme acordamos ..." | "¿Qué acordamos con Acme sobre el plazo?" |
| F3 paraphrase | 20 | a personal fact | shares no content word with the memory |
| F4 changed fact | 30 | the later of two memories about one attribute of one project | asks for the attribute |

Distractors reuse the same projects, clients, people and codes (from a code range no gold memory uses), and
include near misses ("Con Acme hablamos del plazo pero no acordamos nada").

DEV and CONFIRM are disjoint: different random seeds, disjoint code ranges, disjoint (project, attribute)
pairs for F4, and the 40 hand-written paraphrase templates split by index (even to DEV, odd to CONFIRM).
DEV checks that the harness works; CONFIRM is run once and decides.

Sizes: N = 200 and N = 2,000 active memories (accuracy and latency); N = 10,000 for latency only if
building it takes under 15 minutes.

Questions with no answer are left out: `recall` always shows k memories, so retrieval alone cannot score
them.

## Metrics

- Recall@k: share of questions whose gold memory is among the k shown (F4: the later memory).
- MRR@10.
- F4 order: share where the later memory ranks above the earlier one.
- Latency per question, p50 and p95, warm (one question first to load the model and caches), on this PC.
- FTS5 deletion check: after a row is deleted with `secure-delete` on, its unique word must not appear in
  the database bytes.

## Gate (on CONFIRM)

A hybrid arm H (D or E) passes if all hold:

1. Recall@20 of H ≥ Recall@20 of A + 3 points, at both N = 200 and N = 2,000.
2. At N = 2,000, no family's Recall@20 under H is more than 2 points below A's.
3. MRR@10 of H ≥ MRR@10 of A − 0.01 at both sizes.
4. p95 latency of H at N = 2,000 ≤ max(2 × A's p95, A's p95 + 20 ms).
5. For D only: the FTS5 deletion check passes.

If both pass, E is preferred unless D's Recall@20 at N = 2,000 is at least 2 points above E's: FTS5 has to
earn its extra index.

## What each result changes

- **No hybrid passes:** production stays as it is, the FTS5 line is closed, and the next retrieval work
  targets something else (for instance keeping the later version of a changed fact).
- **E passes (and D does not beat it by 2 points):** propose changing `_related` to fuse the meaning ranker
  with `store.search`, with tests, as a product PR. No new index.
- **D passes and beats E by 2 points:** propose an FTS5 index inside the encrypted database, with tests of
  synchronisation, deletion and isolation, as a separate product PR.

## Limits known in advance

Synthetic data written by one author can favour one kind of wording; F3 has only 20 questions per split.
Latency is measured on this PC, not on the server, and leaves out the server's per-request decryption.
A pass is evidence to propose a change, not proof that real people's recall improves.

## Cost

No paid model, no network, no personal data. Code: `observatory/r1_recall_hybrid.py`; results and report in
`docs/` and `artifacts/` on this branch.
