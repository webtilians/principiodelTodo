# INFINITO F12-Q — Factorial de orden, longitud previa y reutilización de instancia

**PRERREGISTRO prospectivo 9 de noviembre de 2026. Este documento debe quedar confirmado en GitHub antes de implementar F12-Q, ejecutar sus pruebas específicas o realizar inferencias reales.**

## Motivación, separación de factores y límites

F12-P-H terminó con `HISTORY_VARIANCE_DETECTED` (H0 PASS/H1 FAIL): el mismo prompt `O21-start` produjo `q0` en 8 de 12 y `q2` en 4 de 12; las salidas `q2` coincidieron con bloque inverso, pero también con su posición y con el historial acumulado. Los otros cinco prompts ancla fueron invariantes en 12/12. F12-O-R había obtenido 60/60 inferencias literalmente idénticas cuando los prompts se repetían agrupados. **Este estudio diagnostica causas sin consultar nuevos mapas.** El estudio F12-P-T de dos nuevas familias queda **intacto y bloqueado**, y no se relanza ni se modifica aquí.

Tres factores cruzados:
- **O, orden de antecedentes:** `AB` frente `BA`, donde `A=O0-start`, `B=O7-start`; el último antecedente inmediato siempre será `C=O0-disabled` para evitar confundir identidad del último prompt con la permutación A/B.
- **P, posición/longitud de bloque:** O21-start en **posición 4** (`A,B,C,target`) o **posición 6** (`D,E,A,B,C,target`, con `D=O7-disabled`, `E=O21-disabled`). En BA se invierten A y B en ambas secuencias. Es un contraste de *posición junto a cantidad/contenido de antecedentes*, no una causa aislada de posición absoluta. Los efectos de P deben etiquetarse `position_and_history_length`.
- **I, instancia:** `reuse`, la misma instancia de FrozenGGUF consume los antecedentes y después O21, frente a `fresh`, que consume antecedentes en una instancia, la destruye y construye una instancia nueva idénticamente parametrizada **antes** de enviar O21. El prompt O21 se envía SOLO a la nueva instancia. Ambos casos ocurren dentro de un **proceso hijo OS nuevo por celda**, para impedir arrastre entre celdas, y se registra la procedencia de la instancia.

Factores O(2)×P(2)×I(2) = **8 celdas**, una réplica de cada celda en **dos trabajadores Linux GitHub Actions independientes** (trabajador 0 ejecuta las celdas en orden lexicográfico, trabajador 1 en orden inverso). Cada celda se ejecuta en su **propio subproceso Python nuevo**, con una instancia nueva al comenzar. Total **16 acciones de O21** y **64 inferencias antecedentes** (80 llamadas reales en total). En `fresh`, segunda carga del mismo GGUF después de destruir primera instancia y `gc.collect()`; capturar parámetros y prueba de objeto nuevo, no afirmar aislamiento de librerías nativas en el mismo proceso. Dos trabajadores contienen resultados independientes para cada celda.

Todos los antecedentes y el target se reconstruyen con `observatory.f12o_repeatability_gate.build_anchors()`, congelados desde F12-N: mismo `SYSTEM`, misma cadena de `O21-start` y mismo SHA256 `b3a52c881af625e9a56166841a334998ec6a366bbb957cb1eabf3c23f099e105`. Ningún cambio de texto ni mensajes acumulados: cada llamada a `create_chat_completion` recibe únicamente ese SYSTEM y el prompt individual (como en F12-P), y por ello se mide estado interno de inferencia, no una conversación explícita. No usar `World` nuevo, ni probar código de Producto.

Mismos parámetros por celda, por modelo y entre los dos trabajadores. Registro por llamada: SHA del prompt y SYSTEM, raw de respuesta, acción parseada, prompt/completion tokens, segundos, tipo de instancia usada, PID del proceso hijo, secuencia/posición y modelo/metadatos.

**Estado de inferencia/caché:** registrar antes/después de la llamada los campos observables de llama-cpp-python `generator.n_tokens`, tipo de `generator.cache` si existe, y `generator.n_ctx()` si se puede consultar, junto con `metadata()` del wrapper. No interpretar `n_tokens` como aciertos de KV-cache. Si la versión fijada no expone contador fiable de cache hits, registrar explícitamente `kv_cache_hits_available=false`, no inventar métricas. ## Gates congelados antes de resultados

- **Q0 completitud/contrato:** 2 workers ×8 celdas únicos, 16 O21 y 64 antecedentes realmente inferidos con mismos 6 prompts/SYSTEM, firmas SHA, 80 raw y JSON válidos, 24 bytes bitácora por celda, trabajadores independientes, un PID hijo distinto por celda dentro de cada worker. Invalidar si hay celda faltante, IDs duplicados, diferencia de source o ausencia de datos de modelo.
- **Q1 modelo idéntico y procedencia:** SHA de pesos, revisión, versión backend, modo temperatura 0, CPU, n_ctx, n_threads, n_batch, seed y max_tokens, tipo de instancia y 8 celda cada worker. En fresh el modelo de O21 debe tener `calls=1` tras su primera llamada; en reuse `calls=previos+1`. Registrar reinicio de instancia y características de cache observables. Cualquier fallo => `INVALID_Q_PROTOCOL`.
- **Q2 replicabilidad por celda:** las dos réplicas de cada celda devuelven exactamente el mismo **raw** en O21. Si una celda difiere, `REPLICATE_VARIANCE` y **no atribuir efectos de O/P/I a factores**.
- **Q3 control cold:** las cuatro celdas `fresh` (ambos trabajadores) devuelven raw idéntico para O21 independientemente de O/P. Si no, `FRESH_VARIANCE` y la interpretación de arrastre queda indeterminada.
- **Q4 efectos O/P/I:** entre las cuatro celdas `reuse` se calcula (a) cambio de salida al invertir A/B a P fijo, (b) cambio al pasar P4→P6 a O fijo, (c) cambio entre reuse/fresh a O/P fijo. Publicar raws, acciones y tasas y clasificarlos: `ORDER_SENSITIVE` si O cambia para alguna P; `POSITION_LENGTH_SENSITIVE` si P cambia para alguna O; `INSTANCE_SENSITIVE` si reuse != fresh para alguna O/P; pueden solaparse. Requerir Q2+Q3 PASS para etiquetar estos contrastes como señales replicadas. Si ninguno cambia => `NO_FACTOR_VARIANCE_OBSERVED`; no demuestra ausencia de ruido en otros entornos.
- **Q5 límites:** observación de cache es diagnóstica; sin contador no inferir hit/miss. Se requiere declarar explícitamente no uso de mundos nuevos de F12-P, ningún cambio de Producto, ni aprendizaje autónomo. No cambiar umbrales tras ver datos.

**Decisión:** `DIAGNOSTIC_SIGNAL` si Q0,Q1,Q2,Q3,Q5 PASS y al menos un contraste Q4 cambia. `DIAGNOSTIC_NO_SIGNAL` si todos PASS y ningún contraste cambia; `INCONCLUSIVE_VARIANCE` si Q0,Q1 PASS pero Q2/Q3 falla; `INVALID_Q_PROTOCOL` si Q0/Q1 falla. Este es **un diagnóstico**, no confirmación científica de causalidad de rendimiento de agentes; no se ejecutará ninguna evaluación de transferencia en esta rama. Más adelante haría falta replicación independiente y observación del backend para atribuir origen interno a caché.
